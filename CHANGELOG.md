## [0.1.0] - 2026-10-12

Initial release of the native Pulumi provider for [Docker Agent](https://docs.docker.com/ai/docker-agent/), built with `pulumi-go-provider` and pinned to `github.com/docker/docker-agent` v1.150.0 (configuration version `"16"`).

### Added

#### Agent configurations and sharing

- `AgentConfig` resource: every key of the docker-agent configuration (version `"16"`) is a typed input, generated from docker-agent's `agent-schema.json` with its descriptions: ordered agents (sub-agents, handoffs, routing, fallback models, harness, cache, hooks, commands, skills, structured output, ...), models (routing, auth, costs, capabilities, thinking and task budgets), custom providers, toolsets of all 30 types, reusable `mcps`, `rag`, `toolsets`, `commands` and `skills` definitions, permissions, sandbox mode (`runtime.sandbox`, `runtime.networkAllowlist`, `runtime.safety`), `budget`/`budgets`, evaluators, flavors and metadata. Each object keeps an `extra` escape hatch for keys of newer docker-agent releases; at the top level, `extra` cannot override a typed section (Check fails instead of silently replacing, for example, `agents`). YAML shorthands map to typed inputs: `simpleCommands` for bare-string commands, `inlineSkills` next to `skills`, `thinkingBudgetTokens` next to `thinkingBudget` and `deferTools` next to `defer`. Renders deterministic YAML and outputs `yaml`, `sha256`, `defaultAgent`, `agentNames`, `requiredEnvVars` and `dockerAgentVersion`. Configurations are validated during preview with the docker-agent loader, including the 30 known toolset types.
- Pulumi enums for the closed value sets of the configuration, generated from `agent-schema.json` with a description per value where docker-agent documents one: `SafetyMode` (agent and `runtime.safety`, also used by `UserSettings`), `HookType`, `HookErrorPolicy`, `LifecycleProfile`, `RestartPolicy`, `ApiType`, `StructuredOutputMode`, `HarnessType`, `HarnessEffort`, `HttpMethod`, `RagStrategyType`, `RagFusionStrategy`, `EvaluatorType`, `EvaluatorDecision` and `EvaluatorFallback`, plus `SidebarPosition`, `SectionSpacing`, `SidebarInfoMode`, `BusySendMode` and `InterruptConfirmation` for `UserSettings`, and `DeleteBehavior`, `ToolApproval` and `Logging` for the provider's own inputs. Go, .NET and Java programs use the typed constants (`dockeragent.SafetyModeBalanced`, `SafetyMode.Balanced`), while TypeScript, Python, YAML and HCL programs can also pass the strings. A value outside the set fails the preview on its property (for example `agents[0].safety`) unless `skipValidation` is set, which accepts values of newer docker-agent releases. Sets that grow with most releases or accept user-defined names stay strings: toolset `type`, webhook `provider` and the model, provider and evaluator `provider`. The upgrade pull request lists removed or renamed enum values, and inputs that became enums, as SDK-breaking changes.
- Check failures point at the Pulumi input (`agents[0].subAgents`, `models["claude"].compactionThreshold`) and report all independent docker-agent problems in one preview: docker-agent stops at the first problem, so the provider removes the faulty value and validates again. `UserSettings` problems carry their property too, and `AgentArtifact`, `AgentRun` and `validateAgentConfig` report every problem of a raw `yaml`. `AgentConfig` warns about literal credentials in `headers` and `env`.
- `AgentArtifact` resource: pushes an agent configuration to an OCI registry with the same wire format as `docker agent share push` (`artifactType` `application/vnd.docker.agent.config.v1+json`, a single gzip-of-YAML layer, `io.docker.agent.version`/`io.docker.cagent.version` annotations, and metadata annotations). Stable `created` timestamp kept in state, drift detection on refresh, `deleteBehavior` `retain` (default) or `delete`, and support for plain-HTTP registries. It warns when a secret `yaml` would be pushed in plaintext.
- `getAgent` function: reads a shared agent by tag or digest, returns its YAML, digest, annotations, metadata and agent names, and writes nothing to disk. Reads artifacts pushed by the `docker agent` CLI.
- `validateAgentConfig` function: validates arbitrary docker-agent YAML and reports errors instead of failing.
- Inputs that are unknown during a preview (because they depend on another resource's output, for example a computed `agents` list of `AgentConfig`) stay unknown for every resource and do not fail the preview.
- `examples/docker-agent-examples`: every example configuration of docker-agent v1.150.0 (200 YAML files and the HCL-only `instructions_from_file.hcl`) as a Pulumi program in TypeScript and in Python, built with typed `AgentConfig` inputs and carrying the comments of the upstream files. `make generate_config_types` generates the programs (`provider/internal/examplegen`), so a docker-agent upgrade regenerates them and its pull request lists the added, removed and changed examples; `make test_examples` type-checks and runs both projects and compares the YAML of every example with golden files.

#### Running agents

- `AgentRun` resource: runs a prompt against an agent configuration (`yaml`, or an OCI `reference` pulled with the provider's registry credentials) during `pulumi up`, in process with the docker-agent Go SDK, and outputs the final answer (`output`), `structuredOutput` (for agents with structured output), `agentName`, `usage` (tokens and estimated cost), `toolCalls` and `ranAt`. It never runs during previews; any input change, including `triggers`, runs it again, and refresh and delete do nothing. Model credentials come from the secret `env` input and, optionally, the environment (`inheritEnvironment`); a secret `env` does not make the answer secret (`outputSecret` does). `toolApproval: deny` (default) only runs tool calls docker-agent approves without asking (read-only tools, `permissions` allow rules, the configuration's own safety mode) and tells the model about the rejected ones; `allow` runs every tool call like `--yolo`. Each run uses private, temporary docker-agent data, config and cache directories and a temporary working directory (or `workingDir`), ignores the user's docker-agent settings, keeps docker-agent's logs (which can quote API errors) off the provider's stderr, and redacts secret inputs from errors. Coding-harness agents are not supported. The provider binary is about 115 MB (about 40 MB without `AgentRun`) because it links docker-agent's runtime with every model provider and toolset.
- `AgentRun` time limits: runs in one provider process execute one at a time, and each is bounded by `timeoutSeconds` (default 300). The `customTimeouts` resource option bounds the whole operation, including pulling a `reference` and waiting for another run; the shorter limit wins.
- `AgentRun` progress: `pulumi up` shows redacted live progress (agents, transfers and handoffs, tool calls and their approval, model fallbacks) and a run summary (duration, tool calls, tokens, estimated cost), controlled by the `logging` input (`none`, `status` (default), `tools`, `full`). With a secret answer, `tools` and `full` log no arguments, messages or results.
- `AgentRun` under `toolApproval: deny` ignores approvals from `pre_tool_use` and `permission_request` hooks; the `allowHookApprovals` input accepts them.
- `AgentRun` with `inheritEnvironment: false` gives command hooks, `shell`/`script`/`background_jobs` tools and MCP/LSP servers started with `command` only system variables plus their own `env`. `docker:` MCP servers, filesystem `post_edit` commands, the `open_url` launcher and docker-agent's on-demand tool installation always inherit the provider environment.
- `AgentRun` errors, warnings and logs also redact credential-named environment variables and `token_key` values; answers that contain one of these values are stored as secrets. Secrets are redacted verbatim and in the escaped forms messages quote them in: JSON strings (tool-call arguments and results are decoded, redacted and encoded again) and Go-quoted strings. With a secret `yaml` or `agent`, warnings, errors and logs name no agents, models or tools.
- `AgentRun` previews show a rerun when an input becomes unknown; changes to `timeoutSeconds`, `outputSecret` or `logging` alone update the state without running the agent again.
- `examples/agent-run-yaml`, tested end to end against a fake OpenAI-compatible server.

#### Local configuration files

- `UserSettings` resource: Docker Agent's user configuration file (`~/.config/cagent/config.yaml`, see [User Settings](https://docs.docker.com/ai/docker-agent/configuration/user-settings/)) with typed inputs for every key of docker-agent's user configuration: the `settings` block (TUI options, `safety`, `permissions`, `hooks`, `keybindings`, `layout`, ...), `aliases`, global `providers`, `defaultModel`, `modelsGateway`, `board`, `credentialHelper` and `sandboxAllowlist`, plus `extra` escape hatches. Identity-token `headers` and hook `env` are secret inputs and stay secret in the state (also when imported or refreshed), and `yaml` and `sha256` are secret with them. It renders the file exactly as docker-agent writes it and validates it with docker-agent's own checks. With `path`, it writes the file atomically (mode 0600), reports changes made outside of Pulumi as drift on refresh and removes it on delete; without `path` it only renders `yaml`. A test fails when a docker-agent upgrade adds a user-configuration key that is not modelled.
- `AgentsIgnore` resource: a [`.agentsignore`](https://docs.docker.com/ai/docker-agent/configuration/agentsignore/) file from ordered `.gitignore`-style `patterns` and an optional `comment`, validated with go-git's gitignore rules (the library docker-agent uses), written to `directory` with the same create, drift and delete behaviour.
- `UserSettings` and `AgentsIgnore` never replace an existing file silently: the preview fails unless `overwrite: true` is set. A file the resource takes over is kept as `<file>.pulumi-backup` (output `backupPath`) and restored on delete.
- `UserSettings` and `AgentsIgnore` keep symbolic links (for example from dotfile managers): the link target is written, refreshed, backed up and restored, and the link itself is never replaced or deleted.
- A managed file deleted outside of Pulumi is reported as drift on refresh and written again by the next `pulumi up`.
- `examples/user-settings-yaml`, tested end to end with the other examples.

#### Importing and converting

- `pulumi import` for `AgentConfig` (from a YAML or HCL file, or an `oci://` artifact read with the provider's registry credentials), `AgentArtifact` (by tag, or by digest), `UserSettings` and `AgentsIgnore`, generating typed code in every language. Only configurations that pass validation are imported (the provider's `skipValidation` imports others and sets `skipValidation: true`); keys without a typed input go to `extra`, `instruction_file` contents become `instruction`, and comments are not kept. Imported files are adopted: the import writes nothing and takes no backup, `overwrite` is not needed, and `pulumi destroy` leaves them in place. `AgentRun` cannot be imported: a run has nothing to read back.
- Converter plugin `pulumi-converter-docker-agent`, released with the provider as six `pulumi-converter-docker-agent-v<version>-<os>-<arch>.tar.gz` archives (a 34 MB binary that does not link docker-agent's runtime). Install it with `pulumi plugin install converter docker-agent v0.1.0 --server github://api.github.com/dirien/pulumi-docker-agent`.
  - `pulumi convert --from docker-agent --language <language>` turns the docker-agent YAML and HCL files of a directory into a program in any Pulumi language, with one typed `AgentConfig` per file. Key order, multi-line strings and comments are kept, anchors are expanded, untyped keys go to `extra`, and instruction files are copied next to the program. It warns about the program generator bugs of Pulumi YAML and Go that affect a file.
  - `-- --push-to <registry>/<namespace>` and `--run "<prompt>"` add an `AgentArtifact` and an `AgentRun` per configuration.
  - `pulumi import --from docker-agent <registry>/<repository>` imports every agent artifact of a repository as an `AgentArtifact`.
  - `examples/convert_test.go` converts all 201 upstream examples, runs the programs and checks that each one renders its golden YAML byte for byte, and compiles a selection of conversions in TypeScript, Python, Go, C#, Java and HCL.

#### Platform integrations

- Policy pack `docker-agent-policies` for Pulumi Policies in `policy/` (TypeScript, `@pulumi/policy`): `agentrun-tool-approval-deny` (mandatory: no `toolApproval: allow` and no `allowHookApprovals`, with a remediation that sets `toolApproval: deny` and `allowHookApprovals: false` and an `allowedResources` exemption), `agentrun-reference-pinned` (advisory), `agentconfig-no-autonomous-safety` (mandatory), `agentconfig-sandbox-for-local-tools` (advisory), `agentconfig-no-literal-credentials` (mandatory), `permissions-no-wildcard-allow` (mandatory: `permissions.allow` of `AgentConfig` and `settings.permissions.allow` of `UserSettings` must not approve every tool or every call of a configurable list of dangerous tools such as `shell`), `usersettings-no-autonomous-safety` (mandatory: no `autonomous` safety or `yolo` in `UserSettings`, globally or per alias), and allowlists for model providers, MCP servers and artifact registries (disabled by default). Violation messages name locations and never repeat URLs, commands or references that may hold credentials (URLs show only scheme and host). Unit tests (`make test_policy`), and `examples/policy_test.go` previews a violating fixture and `examples/yaml` with the pack.
- Documentation for Pulumi ESC: `registryAuth` through `pulumiConfig`, model keys through `environmentVariables` or `env`, `fn::open::aws-login` for Amazon Bedrock, and `pulumi env run` for published agents; `examples/esc-yaml`.
- `examples/automation-ts`: an Automation API inline program that runs `AgentRun` as a CI gate and reads `structuredOutput` with `stack.outputs()`, tested against a fake OpenAI-compatible server.

#### Provider configuration, SDKs and languages

- Provider configuration: `registryAuth` (per-registry credentials, with the Docker credential chain as fallback), `skipValidation` (also `DOCKER_AGENT_SKIP_VALIDATION`) and `forceHttps` (also `DOCKER_AGENT_FORCE_HTTPS`): refuse the plain-HTTP fallback for private (RFC 1918) registry addresses, which would send credentials unencrypted, so that only localhost and loopback registries may use plain HTTP unless a resource sets `insecure: true`.
- SDKs for TypeScript/JavaScript (`@ediri/pulumi-docker-agent`), Python (`ediri_docker_agent`), Go (`github.com/dirien/pulumi-docker-agent/sdk/go/dockeragent`), .NET (`ediri.DockerAgent`) and Java (`io.github.dirien:docker-agent`, package `io.github.dirien.dockeragent`). The Java SDK is built in CI (`make build_java` produces the published jars and POM) and tested end to end (`examples/java`, `TestExampleJava`).
- Pulumi HCL support (`runtime: hcl`): the provider works in Terraform-style `.tf` programs through `required_providers { docker-agent = { source = "pulumi/docker-agent", version = "0.1.0" } }`, with the resources `docker-agent_agent_config`, `docker-agent_agent_artifact`, `docker-agent_agent_run`, `docker-agent_user_settings` and `docker-agent_agents_ignore`, and the data sources `docker-agent_agent` (`getAgent`) and `docker-agent_validate_agent_config` (`validateAgentConfig`). The Registry docs have HCL tabs, and `examples/hcl` is tested end to end with the other examples.

#### Documentation

- Every resource and function has Example Usage in TypeScript, Python, Go, C#, Java, YAML and HCL, generated from Pulumi YAML in `docs/yaml` with `pulumi convert` (`make docs`, part of `make codegen`), and so are the package overview's examples. The API docs describe `pulumi import` for each resource, `AgentRun` logging and time limits, and how validation errors are reported.
- Pulumi Registry search keywords: `cagent`, `genai`, `llm`, `mcp` and `oci`.

#### Maintenance and release

- Typed inputs generated from the pinned `agent-schema.json` (`make generate_config_types`). Tests check that every property of the schema has a typed input, and that all upstream example configurations and an example from every page of the configuration docs can be expressed with typed inputs. CI (`make check_config_types`) fails when the generated types do not match `provider/go.mod`.
- `make upgrade_docker_agent` and the daily `upgrade-docker-agent` workflow: they bump the pinned docker-agent, regenerate the typed inputs, examples, schema and SDKs from the new `agent-schema.json`, run the tests and open a pull request with a report of the configuration schema changes. Every step records its result: when any step fails (`go get`, the generator, `make codegen` or the tests), the pull request is still opened or updated, labelled `needs-attention`, with the failing step and its output. The job that builds the new release has no write access or secrets; a separate job applies the patch (only `provider/`, `sdk/`, `CHANGELOG.md`, `docs/_index.md` and the generated example programs), pushes with git hooks disabled and opens the pull request, also on the next run if opening it failed. Dependabot ignores docker-agent, because a bare `go.mod` bump would skip the regeneration.
- Pull requests and docker-agent upgrade pull requests get a schema-tools SDK breaking-change report and the `breaking-sdk-change` label.
- Provider and converter plugin archives for Linux, macOS and Windows on amd64 and arm64, with checksums, a cosign signature bundle and SBOMs. The release workflow can publish the Java SDK to Maven Central; that is off for this release (`PUBLISH_JAVA: "false"`), so the Java SDK is generated locally with `pulumi package add`.
