## [0.2.0] - TBD

`AgentRun` runs every model provider that docker-agent v1.150.0 supports, with the credentials and SDK behaviour of `docker agent run`: API-key providers and all 26 aliases, Amazon Bedrock, Google Vertex AI, Docker Model Runner, Ollama (local and Ollama Cloud), custom OpenAI-compatible endpoints, and a ChatGPT subscription through `chatgpt/<model>`. Codex agents (`harness: {type: codex}`) run next to Claude Code agents. Each run now runs in a child process of the provider, so `inheritEnvironment: false` also holds for the model SDKs.

### Upgrade notes

Stacks created with v0.1.2 or v0.1.1 upgrade without changes and without running an agent: no input, output or diff of a resource changed, and the schema changes are descriptions only. What changes is how the next run behaves. Check these cases before the first `pulumi up`, and before a `pulumi destroy` of a stack with delete prompts:

- **`inheritEnvironment: false` with model variables in the environment of the Pulumi CLI.** Before v0.2.0, the model SDKs read some variables straight from the provider's process environment, whatever `inheritEnvironment` said. Now a run with `inheritEnvironment: false` sees only `env` and a base environment without credentials (proxies, CA certificates, the Docker connection, the Claude Code and Codex configuration locations, Go and docker-agent settings; see [AgentRun credentials](https://github.com/dirien/pulumi-docker-agent/blob/main/docs/installation-configuration.md#agentrun-credentials)). These variables of the Pulumi CLI's environment therefore no longer reach the models:
  - the base URLs `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL`, `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL`, `AWS_ENDPOINT_URL_BEDROCK_RUNTIME` and `MODEL_RUNNER_HOST`. The requests then go to the provider's default host (for example `https://api.openai.com/v1`) with the key in `env`, so a stack that exported `OPENAI_BASE_URL` for a gateway and passes the gateway's key in `env` would send that key to OpenAI;
  - `OPENAI_API_KEY` for `openai` and `ollama` models that have a `baseUrl` and no `tokenKey` (the OpenAI SDK read it itself);
  - the AWS credentials of `amazon-bedrock` models (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_ROLE_ARN`, `AWS_BEARER_TOKEN_BEDROCK`, ...), for example the ones a Pulumi ESC environment exports with `fn::open::aws-login`;
  - `GOOGLE_APPLICATION_CREDENTIALS` for Vertex AI;
  - the headers `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID`, `OPENAI_CUSTOM_HEADERS` and `ANTHROPIC_CUSTOM_HEADERS`, and `ANTHROPIC_AUTH_TOKEN`, often a gateway's authentication.

  Put them in `env`, where these variables now work (before v0.2.0 the SDKs ignored them there), set the model's `baseUrl`, `tokenKey` or `providerOpts.endpoint_url` in the configuration, or set `inheritEnvironment: true`. The preview warns about every such variable that is set in the environment of the Pulumi CLI and not in `env` ("OPENAI_BASE_URL is set in the environment of the Pulumi CLI, but with inheritEnvironment: false it no longer reaches agents.root.model (openai/gpt-5-mini) since v0.2.0: its requests go to https://api.openai.com/v1; set it in env, or set the model's base_url"), and authentication and connection errors of a run repeat it.
- **Delete prompts that rely on such variables.** `pulumi destroy` previews nothing, and a delete prompt runs with the inputs stored in the state, so a stored `deletePrompt` of an `AgentRun` with `inheritEnvironment: false` whose credentials came from the environment of the Pulumi CLI now fails, and with it the delete. Either run `pulumi up` with the credential in `env` first (that runs the agent again and stores the new `env`), or delete without running the prompt: `DOCKER_AGENT_SKIP_DELETE_PROMPTS=true pulumi destroy`. The error of a failing delete prompt names the variables and both ways.
- **Tool installation with `inheritEnvironment: false`.** docker-agent's on-demand tool installation no longer gets the `GITHUB_TOKEN` or `GH_TOKEN` of the Pulumi CLI's environment, so its requests to the GitHub API are unauthenticated (60 per hour per IP address, which CI runners often share). Pass `GITHUB_TOKEN` in `env`. The Go module settings of its `go install` (`GOPROXY`, `GOFLAGS`, `GOPRIVATE`, `GONOSUMDB`, ...) are kept; the git and SSH variables of direct module downloads (`GIT_*`, `SSH_AUTH_SOCK`) are not.
- **`env` keys in tool processes.** `env` still does not reach the `shell`, `script` and `background_jobs` tools, LSP servers and MCP servers started with `command`. With `inheritEnvironment: true`, a variable that only `env` sets is unset for `shell`, `script` and `background_jobs`, as before, but set to an empty value for LSP servers, for a `shell` toolset with `sudo_askpass` and for a `background_jobs` toolset with `recall`. A program that treats an empty variable differently from an unset one (the AWS CLI with an empty `AWS_PROFILE`, for example) can behave differently there.
- **The processes `AgentRun` cannot control now see `env`.** `docker:` MCP servers (the Docker MCP Gateway), filesystem `post_edit` commands, the `open_url` launcher, docker-agent's on-demand tool installation and docker-agent's helper commands (snapshots, the login shell's `PATH`) inherit the run child's environment: `env` over the environment of the Pulumi CLI, or over the base environment with `inheritEnvironment: false`. Before, they inherited the provider's whole environment, without `env`.
- **Processes that an agent leaves running are stopped.** Before, only the processes of a Claude Code CLI were. Now, when any run ends, `AgentRun` stops what it left running, for example a server that a `shell` tool started in the background, and warns: "the agent run left 1 process running when it ended (for example a command a tool ran in the background); AgentRun stopped it". Start long-lived services outside `AgentRun`.
- **Ctrl-C stops every run within about 2 seconds.** When Pulumi stops the provider (SIGINT), a running agent of any kind now stops within about 2 seconds, and its operation fails with "the agent run was stopped because Pulumi is stopping the provider (SIGINT)". Before, an agent without a coding harness ran on until Pulumi killed the provider 5 seconds later, so a run that ended within those seconds still succeeded.
- **`usage.cost` counts only per-token billing.** A run billed to a subscription reports `0`: a Claude Code agent with the Claude login or `CLAUDE_CODE_OAUTH_TOKEN`, a Codex agent with a ChatGPT login, and `chatgpt/<model>` models. The run summary names the plan instead of a cost. Before, a Claude Code agent reported Claude Code's `total_cost_usd`, an estimate at API prices, also under a subscription. A program that adds up or alerts on `usage.cost` sees lower values.
- **`timeoutSeconds` now covers loading the configuration**, including starting MCP servers and pulling a Docker Model Runner model. A first run that pulls a large model can now time out ("it timed out while pulling the Docker Model Runner model ai/qwen3; pull it first (docker model pull ai/qwen3) or raise timeoutSeconds").
- **Docker Model Runner connects like `docker agent run`**: through the Docker CLI's connection (the current context, `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG` and the TLS variables) instead of the default socket. A `dmr` model without `baseUrl` and `MODEL_RUNNER_HOST` therefore needs a working `docker` CLI with the Model Runner plugin on the machine that runs `pulumi up`.
- **Answers that contain configuration values are no longer secret.** `env` values that are configuration rather than credentials (`AWS_REGION`, `AWS_PROFILE`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_GENAI_USE_VERTEXAI`, `DOCKER_AGENT_DEFAULT_MODEL`, booleans such as `true`, and base URLs without user info, query or fragment) are no longer redacted and no longer make an answer secret. An answer that was stored as a secret only because it contained such a value is stored in plaintext after the next run, or after the next update that only changes the state. Credential-named variables (`*_API_KEY`, `*_TOKEN`, ...) are always secret.
- **Full isolation.** `inheritEnvironment: false` keeps the environment of the Pulumi CLI away from a run, but the SDKs and CLIs still find credentials that are not environment variables: the AWS shared files (`~/.aws/credentials`, `~/.aws/config`, SSO) and the instance metadata service for Bedrock, the gcloud login (`~/.config/gcloud/application_default_credentials.json`) and the metadata server of a Google Cloud machine for Vertex AI, the ChatGPT login of `docker agent setup` for `chatgpt` models, and the logins of the `claude` and `codex` CLIs. The preview warns when a Bedrock or Vertex AI model gets no credentials from `env` and would use them. For a run that uses nothing but `env`, pass the credentials in `env` and switch the machine sources off there: `AWS_EC2_METADATA_DISABLED: "true"`, `AWS_SHARED_CREDENTIALS_FILE: /dev/null` and `AWS_CONFIG_FILE: /dev/null` with `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (and `AWS_SESSION_TOKEN`) or `AWS_BEARER_TOKEN_BEDROCK` for Bedrock; `GOOGLE_APPLICATION_CREDENTIALS` (a service account key file), which wins over the gcloud login, for Vertex AI; `CHATGPT_OAUTH_TOKEN` for `chatgpt` models; `CLAUDE_CODE_OAUTH_TOKEN` for Claude Code; and a `CODEX_HOME` of its own, or `CODEX_API_KEY`, for Codex.

### Added

- Child process isolation. Every run now runs in a child process of the provider: the provider binary started again with a hidden argument, supervised by the provider, in a process group of its own. The child gets a base environment (the provider's whole environment with `inheritEnvironment: true`, otherwise the base variables, which hold no credentials) and receives `env`, the request and secret inputs over a pipe, so the values of `env` never appear in its command line or initial environment, where other processes of the same user could read them (`/proc/<pid>/environ` on Linux, `KERN_PROCARGS2` on macOS). It sets `env` in its own environment before docker-agent starts, so the model SDKs, which read their variables from the process environment, see exactly `env` over the base environment. On Linux the child is not dumpable (no `/proc/<pid>/environ` or ptrace for other processes) and gets SIGTERM when the provider dies (on macOS it stops when its stdin closes). The processes `AgentRun` starts for the configuration (command hooks, `shell`, `script` and `background_jobs` tools, LSP and stdio MCP servers, the Claude Code and Codex CLIs) still get the environment documented in "Where tools run", built from the provider's environment, not the child's. Everything a run left running is stopped when it ends, with a warning. Errors, warnings and logs are redacted twice, in the child and again in the provider. Each run starts one more process.
- Every provider tested. Provider-level tests run every core provider (`openai` with Chat Completions and Responses, `anthropic`, `google` with the Gemini API and Vertex AI, `amazon-bedrock`, `dmr`), all 26 aliases of docker-agent v1.150.0 and custom providers against fake servers that speak each wire protocol: a plain answer, a tool round trip, structured output, usage and cost, the preview, and credentials from `env` and from the inherited environment, plus routing, `first_available`, fallbacks and `auto`. A test fails when a docker-agent upgrade adds an alias without a case. The Installation & Configuration page has a credentials table for every provider and alias, and a docs test fails when that table misses an alias of the pinned docker-agent or names another key variable or endpoint for it.
- ChatGPT subscription. A `chatgpt/<model>` model (or a `models` entry with `provider: chatgpt`) uses the ChatGPT login that `docker agent setup` stores on the machine that runs `pulumi up` (`~/.config/cagent/chatgpt-auth.json`), so a ChatGPT Plus or Pro plan runs the agent in docker-agent's own runtime, with `toolApproval`, `permissions` and redaction, without an API key. For a configuration that names a chatgpt model (as a model, fallback, routing target, `first_available` candidate or compaction model) and whose run's environment does not set `CHATGPT_OAUTH_TOKEN`, `AgentRun` refreshes the login under a lock file (`chatgpt-auth.json.lock`) when its access token is about to expire, copies it into the run's private config directory, and writes a login the run refreshed back to the file when the file did not change meanwhile. The tokens are redacted like credentials. This is the only file of `~/.config/cagent` that `AgentRun` reads or writes. `model: auto` alone never uses the login. The preview warns when there is neither a login nor `CHATGPT_OAUTH_TOKEN`, an error says when another docker agent process refreshed the login at the same time, and the summary reads "no cost estimate (billed to the ChatGPT plan)".
- Codex agents. With `allowHarnessAgents: true`, an agent with `harness: {type: codex}` runs on Linux and macOS: `AgentRun` starts the `codex` CLI (`codex exec --json`, the prompt on stdin) on the machine that runs `pulumi up`, in `workingDir` or a temporary directory, with the Codex login of its `CODEX_HOME` (a ChatGPT plan, without an API key), `CODEX_API_KEY` or `CODEX_ACCESS_TOKEN` in `env`. Unlike Claude Code, `toolApproval` applies: `deny` (the default) runs Codex's commands in its `workspace-write` sandbox without approvals (they can write only in `workingDir` and the temporary directories and reach no network unless `config.toml` allows it, but they can read every file the user can, and MCP servers, hooks and web search run outside the sandbox), and `allow` turns the sandbox off (`--dangerously-bypass-approvals-and-sandbox`). Under `deny`, a check before the first turn (`codex sandbox -- true`) fails the run when the sandbox cannot start, as in most containers. The preview fails when `forced_login_method` of Codex's `config.toml` would make Codex delete its stored login, or `CODEX_HOME` does not exist, and warns about API billing, a missing login, the sandbox, and per agent about the instruction, `structured_output` and the model. `structured_output.strict: true` passes the schema to `codex --output-schema`. After each run, `pulumi up` logs the Codex version, the model, the sandbox, the login, `CODEX_HOME` and the thread, and warns when the run billed API usage. Processes are stopped like those of Claude Code, with SIGINT to Codex first. `pi` and `opencode` harnesses still fail, with a pointer to `chatgpt/<model>` for a ChatGPT subscription.
- Preview credential checks. For a `yaml` configuration known during the preview, and only when the operation runs the agent (a create, a change of an input that affects the run, `rerun: always`), the preview now warns about: variables the configuration needs that `env` (and, when inherited, the environment of the Pulumi CLI) does not set, with a hint when the variable is in the Pulumi CLI's environment but not inherited, or in docker agent's own `~/.config/cagent/.env` (names only); a `first_available` list without a candidate whose credentials are set; the SDK variables of the Pulumi CLI's environment that no longer reach a model with `inheritEnvironment: false`, and those that do with `inheritEnvironment: true` but send a key or header elsewhere (`OPENAI_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, an `OPENAI_API_KEY` for a non-loopback `baseUrl` without `tokenKey`, `OPENAI_ORG_ID` for a non-OpenAI endpoint, ...); Bedrock and Vertex AI models that fall back to the machine's AWS or Google credentials; a missing ChatGPT login; `structured_output` on Amazon Bedrock, which docker-agent does not enforce there (use `mode: tool`); and a Docker models gateway, which `AgentRun` never uses. It logs what `model: auto` resolves to. A configuration pulled by `reference` gets these warnings when it runs. A provider that only user-level configuration declares fails with "AgentRun does not use user-level providers (from docker agent setup, or UserSettings providers): declare the provider under `providers` in the configuration".
- A credential line per run. Unless `logging` is `none`, `pulumi up` shows which models a run can use and where each one's credential comes from, for example `models: openai/gpt-5-mini (OPENAI_API_KEY from env); fallback anthropic/claude-haiku-4-5 (ANTHROPIC_API_KEY from the environment of the Pulumi CLI)`, also for `auto`, `first_available`, routing targets and the SDKs' own fallbacks (an inherited `ANTHROPIC_AUTH_TOKEN`, the AWS and Google default chains, "no key" for a custom provider without `tokenKey`). It names variables, never values. A rejected request (401, 403) repeats it in the error.
- Docker Model Runner parity with `docker agent run`: the Docker CLI's connection (context, host, TLS), `MODEL_RUNNER_HOST` from `env`, the pull of a missing model as a progress line ("pulling the Docker Model Runner model ai/qwen3 (within timeoutSeconds)") and its output in the debug log instead of the provider's stdout, and a pull timeout that says so.
- `DOCKER_AGENT_DEFAULT_MODEL` (or `CAGENT_DEFAULT_MODEL`) in `env`, or in the inherited environment, selects the model of `model: auto` as `provider/model`, as with `docker agent run`.
- `examples/agent-run-ollama-yaml`: a Pulumi YAML program that runs an agent on an Ollama model, local or an Ollama Cloud model through the signed-in local Ollama, with a configurable model and endpoint, tested end to end against a fake OpenAI-compatible server (also that an `OPENAI_API_KEY` of the environment does not reach Ollama). An end-to-end test runs a `chatgpt` model with a ChatGPT login in a temporary home directory against a fake ChatGPT backend. The `AgentRun` API docs have examples for a ChatGPT subscription and for Codex, and the overview's coding-harness example runs a Claude Code and a Codex agent of one configuration.
- Docs: the overview page has new sections "Models and credentials", "Subscription models", "Coding-harness agents (Claude Code and Codex)" and "Not supported"; the Installation & Configuration page has a credentials table for every provider and alias, the base environment of a run, and sections for the ChatGPT subscription, Ollama and Ollama Cloud, Amazon Bedrock and Google Vertex AI, Docker Model Runner, `model: auto`, `UserSettings` and `AgentRun`, the preview checks, and Codex credentials.

### Changed

- `env` values reach the model SDKs. `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` (and the other AWS SDK variables) in `env` now sign Bedrock requests, `GOOGLE_APPLICATION_CREDENTIALS` in `env` authenticates Vertex AI, and base URLs, headers and `MODEL_RUNNER_HOST` in `env` take effect. Before, the SDKs read them only from the provider's process environment.
- A Markdown code fence around a `structured_output` answer is removed for every agent, not only for coding-harness agents (`output` keeps it), and a native-mode answer that is not valid JSON fails with "set structured_output.mode: tool to have docker-agent enforce the schema".
- Errors for missing credentials name the variables and say how to provide them to `AgentRun` (`env`, or `inheritEnvironment: true`) instead of docker-agent's advice for the CLI (`export`, `--env-from-file`, `docker agent setup`). A failed `model: auto` says what it looked for and suggests `DOCKER_AGENT_DEFAULT_MODEL`.
- The run summary says why a run has no cost estimate: "no cost estimate (billed to the ChatGPT plan)", or "no known pricing for the models".
- The tool-approval warning of a delete prompt under `toolApproval: deny` names `permissions` allow rules and `toolApproval: allow` as the ways out; for a Codex agent it explains the sandbox instead.
- The H2 error for unsupported harness types reads "... are not supported by AgentRun yet: only claude-code and codex are; run them with docker agent run (a ChatGPT subscription can also run a chatgpt/<model> model in docker-agent's own runtime, without a coding harness)".

### Fixed

- `inheritEnvironment: false` did not keep credentials of the provider's environment away from the model SDKs: the OpenAI SDK sent the provider's `OPENAI_API_KEY` to the `baseUrl` of an `openai` or `ollama` model without `tokenKey`, the Anthropic SDK added the provider's `ANTHROPIC_AUTH_TOKEN` as a bearer token, and Bedrock and Vertex AI signed with the provider's AWS and Google credentials. The documented promise ("a run depends on nothing but its inputs") now holds for environment variables.
- A ChatGPT subscription (`chatgpt` models) could not use the login of `docker agent setup`: each run's private config directory hid it, and only a short-lived `CHATGPT_OAUTH_TOKEN` in `env` worked.
- `DOCKER_AGENT_DEFAULT_MODEL` was ignored by `model: auto`, and Docker Model Runner dialled the default Docker socket instead of the Docker CLI's context.
- A `structured_output` answer of Amazon Bedrock, which docker-agent sends no schema, failed the run when the model wrapped its JSON in a Markdown code fence.
- Answers that contained a region, a boolean or a base URL from `env` were stored as secrets.
- The pull of a Docker Model Runner model wrote to the provider's stdout, and ran outside `timeoutSeconds`.

### Known issues

- The cost of a request that a rule-based router sends to another model is computed with the price of the router's own model (0 when the router is a custom provider): [docker/docker-agent#4576](https://github.com/docker/docker-agent/issues/4576).

## [0.1.2] - 2026-10-13

### Added

- `AgentRun` runs Claude Code agents. With the new `allowHarnessAgents` input (default `false`), an agent with `harness: {type: claude-code}` (authored with `AgentConfig` as before) runs during `pulumi up` on Linux and macOS: the provider starts the `claude` CLI on the machine that runs Pulumi, so a Claude subscription can run it without an API key, with the machine's `claude` login or a `claude setup-token` token passed as `CLAUDE_CODE_OAUTH_TOKEN` in `env`. The CLI runs in `workingDir` (default: a fresh temporary directory) with the environment that `inheritEnvironment` and `env` describe, gets the prompt on stdin, and runs its own tools without approval: `toolApproval`, `allowHookApprovals` and `permissions` do not apply to it. `output` is Claude Code's final result (when Claude Code reports success with an empty result, the text it wrote during the run, with a warning; without any text, or when it stopped for a deferred tool call, the run fails), and `toolCalls`, `usage` and `usage.cost` come from what it reports. Agents of the types `codex`, `pi` and `opencode`, and every harness on other operating systems, fail with a message that says so.
- Process handling for the Claude Code CLI. Claude Code runs every shell command in a session of its own, outside its process group, and leaves the commands it ran in the background running when it exits. The provider therefore finds the processes started under the CLI in two ways: while the CLI runs, it reads the process table about every 0.2 seconds and records every process below the CLI (by PID and start time, also after the process's parent exited); and the CLI gets a random 128-bit value in `DOCKER_AGENT_RUN_COOKIE`, which every process it starts inherits, so that at each cleanup step the provider also finds the processes of its user that started after the CLI and have exactly that value in their environment (`/proc/<pid>/environ` on Linux, `KERN_PROCARGS2` on macOS), for example `cmd >/dev/null 2>&1 &` run by a shell that exited at once. It stops those processes with the CLI, together with the process groups and sessions they created, whatever Claude Code does with them: on a timeout or cancellation, SIGTERM to the CLI's process group and those processes, and SIGKILL 10 seconds later, or 1 second after the CLI exited if that comes first; after the CLI exited, SIGTERM to what is left and SIGKILL 1 second later, with a warning that says how many processes it left running outside its process group (what is left in the group is stopped without a warning). Each process gets SIGTERM once. Only the processes recorded below the CLI, the groups and sessions they created, and the processes of the provider's user that started after the CLI and carry the exact value are signalled; never a process whose PID was reused, nor the provider's other processes. The environment reads are bounded in number and time. A process is missed only when it left the CLI's process group and session, its parent exited before a read of the process table saw it, and its environment does not show the value: started with `env -i`, or, on macOS, a program whose environment the system does not show to other processes (some signed programs under System Integrity Protection). When the process table cannot be read, only the CLI's process group and what was recorded until then are stopped. After the CLI exited, the output is read for at most 2 more seconds. When Pulumi stops the provider (SIGINT), no new CLI starts and the running ones and their processes get SIGTERM and SIGKILL 2 seconds later; the provider still shuts down through the Pulumi SDK, after the operations that ran them. When the provider dies (SIGKILL, a crash), nothing stops these processes; on Linux the CLI itself gets SIGTERM from the kernel. The markers of a parent Claude Code session and the variables it sets for its processes (`TRACEPARENT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_TMPDIR`, ...) are removed from the CLI's environment. The CLI's error output is redacted and shortened in errors, and errors end with a hint for an expired or missing login, a login refreshed by another Claude Code process at the same time, and running as root.
- Billing and root warnings. The preview (for a `yaml` configuration that the provider's docker-agent version loads, also with `skipValidation`) warns when the CLI would get `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` (which Claude Code bills instead of the subscription), `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` or `ANTHROPIC_BASE_URL`, naming the variable but never its value, when the provider runs as root without `IS_SANDBOX=1`, and when `inheritEnvironment: false` keeps a `CLAUDE_CODE_OAUTH_TOKEN` of the Pulumi CLI's environment from the CLI while `env` does not set one (the CLI then uses the login of the machine; the log line after the run and an authentication or login-refresh error say so too; an empty `CLAUDE_CODE_OAUTH_TOKEN` in `env` keeps the login without the warning). An inherited `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` is not passed to the CLI when `env` sets `CLAUDE_CODE_OAUTH_TOKEN`. After each run, `pulumi up` logs the Claude Code version, the model and the reported `apiKeySource` (for `none`, also what the environment selects instead: the Claude login, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN` or a cloud provider), and warns when the run billed API usage or a cloud account. An empty inherited `ANTHROPIC_API_KEY` is not reported as dropped. The preview also warns that a harness agent's `instruction` is not sent, that its `structured_output` is not enforced, and when `harness.model` is missing and docker-agent would pass a `models` key or a model of another provider than `anthropic` to `claude --model`.
- `AgentRun` inputs `updatePrompt`, the message of a rerun while `prompt` is unchanged (a rerun after a change of `prompt` sends `prompt`), and `deletePrompt`, which runs when the resource is deleted (`pulumi destroy`, removal from the program, the old resource of a replacement) with the inputs stored in the state. A failing delete prompt fails the delete. `DOCKER_AGENT_SKIP_DELETE_PROMPTS=true` skips the delete prompts of one `pulumi` command with a warning, and a delete prompt is also skipped with a warning when `workingDir` no longer exists or is no longer a directory, or when another `AgentRun` of the same provider ran in that `workingDir` during the same command, also while the delete prompt waited for it. The warning does not show a secret `workingDir`. With `toolApproval: deny`, the preview warns that the delete prompt of an agent without a coding harness can only run read-only tools and the calls that `permissions` allow.
- `AgentRun` input `rerun` with the enum `RerunPolicy`: `onChange` (default) and `always`, which runs the agent again on every `pulumi up` that includes the resource, with `updatePrompt`. `pulumi refresh`, `pulumi refresh --run-program` and the refresh of `pulumi up --refresh` report no drift for it.
- Changes of `updatePrompt`, `deletePrompt`, `allowHarnessAgents` and `rerun` (unless it becomes `always`) only update the state.
- New `AgentRun`s get unique IDs (`<name>-<8 hex digits>`), so `pulumi state delete` can tell a resource from its pending-delete copy. Existing `AgentRun`s keep their IDs.
- `examples/agent-run-claude-code-ts`: an `AgentConfig` with a Claude Code harness and two `AgentRun`s of it (create, update and delete prompts in a working directory, `rerun`, and a second run chained with `triggers`), tested end to end with a fake `claude` on a restricted `PATH`. The overview page has new sections "Reruns and delete prompts", "One agent, several runs" and "Coding-harness agents (Claude Code)", the Installation & Configuration page has "Claude Code credentials", and the `AgentRun` API docs have examples for Claude Code and for several runs of one agent.
- Policy pack: `agentrun-tool-approval-deny` also reports `allowHarnessAgents: true` on `AgentRun`s that are not in `allowedResources`, and its remediation sets it to `false`.

### Changed

- The preview error for a coding-harness agent without the opt-in names `allowHarnessAgents`.
- The progress shows the tool calls of a Claude Code agent as "run by the harness" (or "run by the harness, failed") instead of approved or rejected.
- When a `deletePrompt` is stored, the `AgentRun` diff asks for delete-before-replace, so a replacement that Pulumi decides from the provider's diff (`replaceOnChanges`) runs the old delete prompt before the new create.
- When `customTimeouts` runs out, a run fails with "the operation's time limit (customTimeouts) ran out before the agent finished" instead of "the agent run was canceled".
- Stacks created with v0.1.1 upgrade without changes and without running an agent, also when the program pins the provider version, as the SDKs do (tested against the released v0.1.1 plugin). Their `rerun` and `allowHarnessAgents` outputs stay undefined until the next update of the resource. The SDK changes are additive.

### Fixed

- Provider configuration changes no longer replace resources. pulumi-go-provider replaces a provider on any change of its configuration, and Pulumi then replaces every resource of the provider: every `AgentConfig`, `AgentArtifact`, `UserSettings`, `AgentsIgnore` and `AgentRun` was replaced and every `AgentRun` ran again (with a `deletePrompt`, the old resource's delete prompt would then undo the new run). This happened when a setting changed (a rotated `registryAuth` password, an added `registryAuth` entry, `forceHttps` or `skipValidation`, also only through `DOCKER_AGENT_FORCE_HTTPS` or `DOCKER_AGENT_SKIP_VALIDATION` in the environment of one command), on every upgrade of the provider version of a program that pins it, as the generated SDKs do (pulumi-go-provider's internal `__pulumi-go-provider-*` keys were reported as deleted), and when resources moved to another provider instance. Every change now updates the provider in place, and Pulumi configures it with the new settings in the same command. (Right after `pulumi import`, a setting added before the next `pulumi up` takes effect in that command but is shown as a provider change only in the following one.) Since the new provider decides, this also covers the upgrade from v0.1.1.
- A null value where a map value or a list element is expected (for example `env: {X: null}` in TypeScript, or `None` in Python) crashed the provider (`reflect: call of reflect.Value.Type on zero Value` in pulumi-go-provider's input decoding) for every resource, function and the provider configuration. A null map value now counts as an absent key, a null list element fails the preview with its path (for example `agents[1].toolsets[0]: a list element must not be null`), and values that take any type (`extra`, `providerOpts`, `triggers`) keep their nulls. A panic while checking inputs is reported as a failure instead of ending the provider. Pulumi YAML programs were not affected: they drop `X: null` from a map.
- An `AgentRun` whose run made no tool calls got stuck after an update that did not run the agent (a change of only `timeoutSeconds`, `outputSecret` or `logging`): that update dropped the empty `toolCalls` list from the state, and every later diff, update and delete of the resource failed to read the state. Such updates keep the list now, and a state written that way by v0.1.1 is read with an empty `toolCalls` again, so its stack works without a manual state edit.

## [0.1.0] - 2026-10-12

Initial release of the native Pulumi provider for [Docker Agent](https://docs.docker.com/ai/docker-agent/), built with `pulumi-go-provider` and pinned to `github.com/docker/docker-agent` v1.150.0 (configuration version `"16"`).

### Added

#### Agent configurations and sharing

- `AgentConfig` resource: every key of the docker-agent configuration (version `"16"`) is a typed input, generated from docker-agent's `agent-schema.json` with its descriptions: ordered agents (sub-agents, handoffs, routing, fallback models, harness, cache, hooks, commands, skills, structured output, ...), models (routing, auth, costs, capabilities, thinking and task budgets), custom providers, toolsets of all 30 types, reusable `mcps`, `rag`, `toolsets`, `commands` and `skills` definitions, permissions, sandbox mode (`runtime.sandbox`, `runtime.networkAllowlist`, `runtime.safety`), `budget`/`budgets`, evaluators, flavors and metadata. Each object keeps an `extra` escape hatch for keys of newer docker-agent releases; at the top level, `extra` cannot override a typed section (Check fails instead of silently replacing, for example, `agents`). YAML shorthands map to typed inputs: `simpleCommands` for bare-string commands, `inlineSkills` next to `skills`, `thinkingBudgetTokens` next to `thinkingBudget` and `deferTools` next to `defer`. Renders deterministic YAML and outputs `yaml`, `sha256`, `defaultAgent`, `agentNames`, `requiredEnvVars` and `dockerAgentVersion`. Configurations are validated during preview with the docker-agent loader, including the 30 known toolset types.
- Pulumi enums for the closed value sets of the configuration, generated from `agent-schema.json` with a description per value where docker-agent documents one: `SafetyMode` (agent and `runtime.safety`, also used by `UserSettings`), `HookType`, `HookErrorPolicy`, `LifecycleProfile`, `RestartPolicy`, `ApiType`, `StructuredOutputMode`, `HarnessType`, `HarnessEffort`, `HttpMethod`, `RagStrategyType`, `RagFusionStrategy`, `EvaluatorType`, `EvaluatorDecision` and `EvaluatorFallback`, plus `SidebarPosition`, `SectionSpacing`, `SidebarInfoMode`, `BusySendMode` and `InterruptConfirmation` for `UserSettings`, and `DeleteBehavior`, `ToolApproval` and `Logging` for the provider's own inputs. Go, .NET and Java programs use the typed constants (`dockeragent.SafetyModeBalanced`, `SafetyMode.Balanced`), while TypeScript, Python, YAML and HCL programs can also pass the strings. A value outside the set fails the preview on its property (for example `agents[0].safety`) unless `skipValidation` is set, which accepts values of newer docker-agent releases. Sets that grow with most releases or accept user-defined names stay strings: toolset `type`, webhook `provider` and the model, provider and evaluator `provider`. The upgrade pull request lists removed or renamed enum values, and inputs that became enums, as SDK-breaking changes.
- Check failures point at the Pulumi input (`agents[0].subAgents`, `models["claude"].compactionThreshold`) and report all independent docker-agent problems in one preview: docker-agent stops at the first problem, so the provider removes the faulty value and validates again. `UserSettings` problems carry their property too, and `AgentArtifact`, `AgentRun` and `validateAgentConfig` report every problem of a raw `yaml`. `AgentConfig` warns about literal credentials in `headers` and `env`.
- `AgentArtifact` resource: pushes an agent configuration to an OCI registry with the same wire format as `docker agent share push` (`artifactType` `application/vnd.docker.agent.config.v1+json`, a single gzip-of-YAML layer, `io.docker.agent.version`/`io.docker.cagent.version` annotations, and metadata annotations). Stable `created` timestamp kept in state, drift detection on refresh, `deleteBehavior` `retain` (default) or `delete`, and support for plain-HTTP registries. It warns when a secret `yaml` would be pushed in plaintext.
- `getAgent` function: reads a shared agent by tag or digest, returns its YAML, digest, annotations, metadata and agent names, and writes nothing to disk. Reads artifacts pushed by the `docker agent` CLI.
- `validateAgentConfig` function: validates arbitrary docker-agent YAML and reports errors instead of failing.
- Inputs that are unknown during a preview (because they depend on another resource's output, for example a computed `agents` list of `AgentConfig`) stay unknown for every resource and do not fail the preview.
- `examples/docker-agent-examples`: every example configuration of docker-agent v1.150.0 (200 YAML files and the HCL-only `instructions_from_file.hcl`) as a Pulumi program in TypeScript and in Python, built with typed `AgentConfig` inputs and carrying the comments of the upstream files. `make generate_config_types` generates the programs (`provider/internal/examplegen`), so a docker-agent upgrade regenerates them and its pull request lists the added, removed and changed examples; `make test_examples` type-checks and runs both projects and compares the YAML of every example with golden files.

#### Running agents

- `AgentRun` resource: runs a prompt against an agent configuration (`yaml`, or an OCI `reference` pulled with the provider's registry credentials) during `pulumi up`, in process with the docker-agent Go SDK, and outputs the final answer (`output`), `structuredOutput` (for agents with structured output), `agentName`, `usage` (tokens and estimated cost), `toolCalls` and `ranAt`. It never runs during previews; any input change, including `triggers`, runs it again, and refresh and delete do nothing. Model credentials come from the secret `env` input and, optionally, the environment (`inheritEnvironment`); a secret `env` does not make the answer secret (`outputSecret` does). `toolApproval: deny` (default) only runs tool calls docker-agent approves without asking (read-only tools, `permissions` allow rules, the configuration's own safety mode) and tells the model about the rejected ones; `allow` runs every tool call like `--yolo`. Each run uses private, temporary docker-agent data, config and cache directories and a temporary working directory (or `workingDir`), ignores the user's docker-agent settings, keeps docker-agent's logs (which can quote API errors) off the provider's stderr, and redacts secret inputs from errors. Coding-harness agents are not supported. The provider binary is about 115 MB (about 40 MB without `AgentRun`) because it links docker-agent's runtime with every model provider and toolset.
- `AgentRun` time limits: runs in one provider process execute one at a time, and each is bounded by `timeoutSeconds` (default 300). The `customTimeouts` resource option bounds the whole operation, including pulling a `reference` and waiting for another run; the shorter limit wins.
- `AgentRun` progress: `pulumi up` shows redacted live progress (agents, transfers and handoffs, tool calls and their approval, model fallbacks) and a run summary (duration, tool calls, tokens, estimated cost), controlled by the `logging` input (`none`, `status` (default), `tools`, `full`). With a secret answer, `tools` and `full` log no arguments, messages or results.
- `AgentRun` under `toolApproval: deny` ignores approvals from `pre_tool_use` and `permission_request` hooks; the `allowHookApprovals` input accepts them.
- `AgentRun` with `inheritEnvironment: false` gives command hooks, `shell`/`script`/`background_jobs` tools and MCP/LSP servers started with `command` only system variables plus their own `env`. `docker:` MCP servers, filesystem `post_edit` commands, the `open_url` launcher and docker-agent's on-demand tool installation always inherit the provider environment.
- `AgentRun` errors, warnings and logs also redact credential-named environment variables and `token_key` values; answers that contain one of these values are stored as secrets. Secrets are redacted verbatim and in the escaped forms messages quote them in: JSON strings (tool-call arguments and results are decoded, redacted and encoded again) and Go-quoted strings. With a secret `yaml` or `agent`, warnings, errors and logs name no agents, models or tools.
- `AgentRun` previews show a rerun when an input becomes unknown; changes to `timeoutSeconds`, `outputSecret` or `logging` alone update the state without running the agent again.
- `examples/agent-run-yaml`, tested end to end against a fake OpenAI-compatible server.

#### Local configuration files

- `UserSettings` resource: Docker Agent's user configuration file (`~/.config/cagent/config.yaml`, see [User Settings](https://docs.docker.com/ai/docker-agent/configuration/user-settings/)) with typed inputs for every key of docker-agent's user configuration: the `settings` block (TUI options, `safety`, `permissions`, `hooks`, `keybindings`, `layout`, ...), `aliases`, global `providers`, `defaultModel`, `modelsGateway`, `board`, `credentialHelper` and `sandboxAllowlist`, plus `extra` escape hatches. Identity-token `headers` and hook `env` are secret inputs and stay secret in the state (also when imported or refreshed), and `yaml` and `sha256` are secret with them. It renders the file exactly as docker-agent writes it and validates it with docker-agent's own checks. With `path`, it writes the file atomically (mode 0600), reports changes made outside of Pulumi as drift on refresh and removes it on delete; without `path` it only renders `yaml`. A test fails when a docker-agent upgrade adds a user-configuration key that is not modelled.
- `AgentsIgnore` resource: a [`.agentsignore`](https://docs.docker.com/ai/docker-agent/configuration/agentsignore/) file from ordered `.gitignore`-style `patterns` and an optional `comment`, validated with go-git's gitignore rules (the library docker-agent uses), written to `directory` with the same create, drift and delete behaviour.
- `UserSettings` and `AgentsIgnore` never replace an existing file silently: the preview fails unless `overwrite: true` is set. A file the resource takes over is kept as `<file>.pulumi-backup` (output `backupPath`) and restored on delete.
- `UserSettings` and `AgentsIgnore` keep symbolic links (for example from dotfile managers): the link target is written, refreshed, backed up and restored, and the link itself is never replaced or deleted.
- A managed file deleted outside of Pulumi is reported as drift on refresh and written again by the next `pulumi up`.
- `examples/user-settings-yaml`, tested end to end with the other examples.

#### Importing and converting

- `pulumi import` for `AgentConfig` (from a YAML or HCL file, or an `oci://` artifact read with the provider's registry credentials), `AgentArtifact` (by tag, or by digest), `UserSettings` and `AgentsIgnore`, generating typed code in every language. Only configurations that pass validation are imported (the provider's `skipValidation` imports others and sets `skipValidation: true`); keys without a typed input go to `extra`, `instruction_file` contents become `instruction`, and comments are not kept. Imported files are adopted: the import writes nothing and takes no backup, `overwrite` is not needed, and `pulumi destroy` leaves them in place. `AgentRun` cannot be imported: a run has nothing to read back.
- Converter plugin `pulumi-converter-docker-agent`, released with the provider as six `pulumi-converter-docker-agent-v<version>-<os>-<arch>.tar.gz` archives (a 34 MB binary that does not link docker-agent's runtime). Install it with `pulumi plugin install converter docker-agent v0.1.0 --server github://api.github.com/dirien/pulumi-docker-agent`.
  - `pulumi convert --from docker-agent --language <language>` turns the docker-agent YAML and HCL files of a directory into a program in any Pulumi language, with one typed `AgentConfig` per file. Key order, multi-line strings and comments are kept, anchors are expanded, untyped keys go to `extra`, and instruction files are copied next to the program. It warns about the program generator bugs of Pulumi YAML and Go that affect a file.
  - `-- --push-to <registry>/<namespace>` and `--run "<prompt>"` add an `AgentArtifact` and an `AgentRun` per configuration.
  - `pulumi import --from docker-agent <registry>/<repository>` imports every agent artifact of a repository as an `AgentArtifact`.
  - `examples/convert_test.go` converts all 201 upstream examples, runs the programs and checks that each one renders its golden YAML byte for byte, and compiles a selection of conversions in TypeScript, Python, Go, C#, Java and HCL.

#### Platform integrations

- Policy pack `docker-agent-policies` for Pulumi Policies in `policy/` (TypeScript, `@pulumi/policy`): `agentrun-tool-approval-deny` (mandatory: no `toolApproval: allow` and no `allowHookApprovals`, with a remediation that sets `toolApproval: deny` and `allowHookApprovals: false` and an `allowedResources` exemption), `agentrun-reference-pinned` (advisory), `agentconfig-no-autonomous-safety` (mandatory), `agentconfig-sandbox-for-local-tools` (advisory), `agentconfig-no-literal-credentials` (mandatory), `permissions-no-wildcard-allow` (mandatory: `permissions.allow` of `AgentConfig` and `settings.permissions.allow` of `UserSettings` must not approve every tool or every call of a configurable list of dangerous tools such as `shell`), `usersettings-no-autonomous-safety` (mandatory: no `autonomous` safety or `yolo` in `UserSettings`, globally or per alias), and allowlists for model providers, MCP servers and artifact registries (disabled by default). Violation messages name locations and never repeat URLs, commands or references that may hold credentials (URLs show only scheme and host). Unit tests (`make test_policy`), and `examples/policy_test.go` previews a violating fixture and `examples/yaml` with the pack.
- Documentation for Pulumi ESC: `registryAuth` through `pulumiConfig`, model keys through `environmentVariables` or `env`, `fn::open::aws-login` for Amazon Bedrock, and `pulumi env run` for published agents; `examples/esc-yaml`.
- `examples/automation-ts`: an Automation API inline program that runs `AgentRun` as a CI gate and reads `structuredOutput` with `stack.outputs()`, tested against a fake OpenAI-compatible server.

#### Provider configuration, SDKs and languages

- Provider configuration: `registryAuth` (per-registry credentials, with the Docker credential chain as fallback), `skipValidation` (also `DOCKER_AGENT_SKIP_VALIDATION`) and `forceHttps` (also `DOCKER_AGENT_FORCE_HTTPS`): refuse the plain-HTTP fallback for private (RFC 1918) registry addresses, which would send credentials unencrypted, so that only localhost and loopback registries may use plain HTTP unless a resource sets `insecure: true`.
- SDKs for TypeScript/JavaScript (`@ediri/pulumi-docker-agent`), Python (`ediri_docker_agent`), Go (`github.com/dirien/pulumi-docker-agent/sdk/go/dockeragent`), .NET (`ediri.DockerAgent`) and Java (`io.github.dirien:docker-agent`, package `io.github.dirien.dockeragent`). The Java SDK is built in CI (`make build_java` produces the published jars and POM) and tested end to end (`examples/java`, `TestExampleJava`).
- Pulumi HCL support (`runtime: hcl`): the provider works in Terraform-style `.tf` programs through `required_providers { docker-agent = { source = "pulumi/docker-agent", version = "0.1.0" } }`, with the resources `docker-agent_agent_config`, `docker-agent_agent_artifact`, `docker-agent_agent_run`, `docker-agent_user_settings` and `docker-agent_agents_ignore`, and the data sources `docker-agent_agent` (`getAgent`) and `docker-agent_validate_agent_config` (`validateAgentConfig`). The Registry docs have HCL tabs, and `examples/hcl` is tested end to end with the other examples.

#### Documentation

- Every resource and function has Example Usage in TypeScript, Python, Go, C#, Java, YAML and HCL, generated from Pulumi YAML in `docs/yaml` with `pulumi convert` (`make docs`, part of `make codegen`), and so are the package overview's examples. The API docs describe `pulumi import` for each resource, `AgentRun` logging and time limits, and how validation errors are reported.
- Pulumi Registry search keywords: `cagent`, `genai`, `llm`, `mcp` and `oci`.

#### Maintenance and release

- Typed inputs generated from the pinned `agent-schema.json` (`make generate_config_types`). Tests check that every property of the schema has a typed input, and that all upstream example configurations and an example from every page of the configuration docs can be expressed with typed inputs. CI (`make check_config_types`) fails when the generated types do not match `provider/go.mod`.
- `make upgrade_docker_agent` and the daily `upgrade-docker-agent` workflow: they bump the pinned docker-agent, regenerate the typed inputs, examples, schema and SDKs from the new `agent-schema.json`, run the tests and open a pull request with a report of the configuration schema changes. Every step records its result: when any step fails (`go get`, the generator, `make codegen` or the tests), the pull request is still opened or updated, labelled `needs-attention`, with the failing step and its output. The job that builds the new release has no write access or secrets; a separate job applies the patch (only `provider/`, `sdk/`, `CHANGELOG.md`, `docs/_index.md` and the generated example programs), pushes with git hooks disabled and opens the pull request, also on the next run if opening it failed. Dependabot ignores docker-agent, because a bare `go.mod` bump would skip the regeneration.
- Pull requests and docker-agent upgrade pull requests get a schema-tools SDK breaking-change report and the `breaking-sdk-change` label.
- Provider and converter plugin archives for Linux, macOS and Windows on amd64 and arm64, with checksums, a cosign signature bundle and SBOMs. The release workflow can publish the Java SDK to Maven Central; that is off for this release (`PUBLISH_JAVA: "false"`), so the Java SDK is generated locally with `pulumi package add`.
